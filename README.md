# 病院のサイバー問診アシスタント

その「はい」、本当に大丈夫？ ― サイバーセキュリティ対策を、専門家の目でもう一度

Built with Claude: Japan 2026 の提出作品です（テーマ2「本来、誰にでも届くべきものを。」）。

中小病院でチェックリストを担当する事務職員のための Web アプリです。「はい」の裏に隠れた、サイバー攻撃で診療が止まるおそれがあるところを、問診で見つけます。さらに、保守ベンダーとのやりとりを通訳して、足りない備えを一緒に整えていきます。

公開 URL：https://cyber-monshin.vercel.app/ （検証中は、試すのに合言葉が必要です）

> このアプリは点検を助けるもので、対策の準拠を保証したり、法的な判断をしたりしません。厚生労働省の公式ツールではありません。サンプルの黒戸（くろうど）記念病院と黒戸町は架空です。

## 作者より

日本は、高齢化と人手不足に世界に先がけて向き合う「課題先進国」です。ヘルスケアと IT は、その最前線の一つだと感じています。医療機関のサイバーセキュリティ対策には、国、自治体、医療機関、ベンダーなど多くの人が関わり、そのぶん責任の境目に抜けが生まれやすい。日々の中でそう気づき、大事だと考えてきました。そこで、人も予算も足りない病院でも、専門家に頼らずに備えを確かめられるアシスタントを作りました。

## なぜ作るのか

### 「はい」と書くしかない人がいる

よくある場面をもとにした、架空の例です。

100床ほどの病院で、事務長がシステムの担当を兼ねています。IT の専門家ではありません。技術のことは、保守を頼んでいるベンダーに任せています。

毎年の立入検査の前に、事務長は厚生労働省のサイバーセキュリティ対策チェックリストを埋めます。「バックアップを確保のうえ、復旧手順を確認している」という欄には、ベンダーに電話で聞いて「はい」と書きます。

けれども、本当にデータを戻せるのか、攻撃を受けても控えが無事なのかは、誰も確かめていません。事務長には、何をどう確かめればよいのかが分からないからです。ベンダーの説明は専門用語ばかりで、聞き返すこともできません。

### その「はい」の裏で、病院が止まる

病院を狙うサイバー攻撃が相次いでいます。入口は、保守のために外部とつながる機器や回線、更新されていない機器、使い回されたパスワードなどです。一度入られると被害は院内に広がり、電子カルテが使えなくなれば、外来や救急が止まりかねません。

代表的なのはランサムウェアです。データを使えなくして、身代金を求めます。バックアップがふだんの機器につながったままだと、バックアップも使えなくなり、データを戻せないおそれがあります。国内でも、とある病院で電子カルテが使えなくなり、長いあいだ通常の診療ができなくなりました。

このアプリが確かめる重点項目5つは、この流れ（入られる、広がる、戻せない、止まる）に沿って選んでいます。

チェックリストは「はい／いいえ」の自己点検です。確かめ方を知らないまま「はい」と書けば、足りない備えは見過ごされます。

### これは、特別な病院の話ではない

確かめ方が分からないまま「はい」と書く状況は、一部の病院だけのことではありません。

日本の病院の多くは、中小病院です。全国の病院8,001施設のうち、20〜199床の病院は5,638施設で、約7割を占めます（2025年10月1日時点）。

そして、システムを守る専任の職員が0人か1人しかいない病院が、全体の約半数、20〜199床の病院では約6割にのぼります。400床以上の病院の約1割とは、大きな差があります（厚生労働省の調査に回答した5,736病院、2026年3月末時点）。

事務の担当者が「はい」の中身を確かめようとすると、次のような困りごとにぶつかります。

| 困りごと | 調査の数字（2026年3月末時点、回答した病院） |
| --- | --- |
| 守る人が足りない | 情報システム部門に常勤で専任の職員が0〜1人の病院は、全体で約50%、20〜199床で約59%、400床以上で約11%。「常勤で専任」は、就業時間の5割以上をその仕事に充てる職員のこと |
| 専門知識が足りない | 20〜199床の病院で、医療情報システム安全管理責任者（システムの安全を受け持つ人）のうち、情報処理に関する資格を持つ人は約14% |
| 「はい」の裏が見えない | サイバー攻撃を想定した事業継続計画（BCP。非常時にも診療を続けるための計画）を作った病院は74.6%。そのうち訓練まで行った病院は43.1% |
| 役割分担が見えにくい | 病院とベンダーの役割を確かめる「役割分担確認表」を知らない病院は43.7%。使ったことがある病院は約9% |

「約」を付けた割合と「約7割」は、資料の件数や割合から計算した値です。調査の数字は回答した病院の集計で、全国すべての病院の実数ではありません。

出典：[「病院における医療情報システムのサイバーセキュリティ対策に係る調査」の結果について](https://www.mhlw.go.jp/content/10808000/001705951.pdf)（厚生労働省、2026年5月29日）、[医療施設（動態）調査 令和7年](https://www.mhlw.go.jp/toukei/saikin/hw/iryosd/25/dl/02sisetu07.pdf)（厚生労働省）をもとに作成

### これから、支える力はさらに足りなくなる

地域の病院の役割は、これから大きくなります。2020年から2040年に、85歳以上の救急搬送は75%増え、在宅医療の需要は62%増えると見込まれています。

一方で、支える人は減っていきます。2025年から2040年に、働く世代は全国で15.0%、過疎地域型（資料の地域の区分）では28.4%減ると見込まれています。医療と福祉の働き手は、2040年に1,070万人が必要とされています。経済が成長し、働く人が増えた場合でも、確保できるのは974万人で、96万人足りない見込みです。

経営の面でも余力がありません。病院団体の調査では、回答した1,498病院のうち74.6%が、2024年度に、診療の収入より費用が多い赤字（医業収支の赤字）でした。

人も費用も足りないなかで、中小病院がシステムを守る専任の職員を新しく雇うことは、これからいっそう難しくなると考えられます。専門家の点検は有償なので、余力のない病院ほど届きにくくなります。地域の病院が止まれば、その地域の住民が医療を受けにくくなります。

出典：[新たな地域医療構想を通じて目指すべき医療について](https://www.mhlw.go.jp/content/10800000/001294917.pdf)（厚生労働省）、[令和4年版 厚生労働白書 第1部第1章](https://www.mhlw.go.jp/wp/hakusyo/kousei/21/dl/1-01.pdf)（厚生労働省）、[2025年度病院経営定期調査](https://ajhc.or.jp/siryo/20251126report.pdf)（日本病院会、全日本病院協会、日本医療法人協会、日本精神科病院協会）をもとに作成

### 国も、病院に備えを求め、支えるための予算を要求している

国は、病院のサイバー対策を急いでいます。

| いつ | 国の動き |
| --- | --- |
| 令和5年（2023年）4月 | 医療法施行規則の改正で、病院の管理者（院長など）にサイバー攻撃への対策が義務づけられた |
| 令和5年（2023年）6月 | 医療法にもとづく立入検査で、チェックリストへの記入を確かめるようになった |
| 令和8年度（2026年度）の診療報酬改定 | 新しい加算（電子的診療情報連携体制整備加算1）の条件に、次の3つが入った<br>・医療情報システム安全管理責任者を専任で置く<br>・バックアップを複数の方法で取り、一部をネットワークから切り離して保管する<br>・BCP（事業継続計画）を作り、年1回ほど訓練する |
| 令和9年度（2027年度）の概算要求 | 医療機関のサイバー対策に137億円を要求した（令和8年度の当初予算は1億円、ほかに令和7年度の補正予算で15億円） |

概算要求は、各省が次の年度に向けて出す予算の要求で、まだ決まった額ではありません。

要求の資料は、多くの病院で外部とのつながりがベンダーごとにばらばらで、病院が把握できていないことを課題に挙げ、入口を減らす工事などへの補助を求めています。20〜199床の病院は上限2,100万円、補助率は10分の10（国が全額を出す）です（いずれも要求の段階）。

決まりや補助ができても、使うのは病院です。「はい」を確かめ、ベンダーと話し、補助を使うかを考えるのは、専任ではない事務の担当者であることが少なくありません。

出典：[令和9年度 政策統括官（情報政策担当）関係 概算要求](https://www.mhlw.go.jp/wp/yosan/yosan/27syokan/dl/gaiyo-15-1.pdf)、[同 参考資料（医療機関におけるサイバーセキュリティ確保事業）](https://www.mhlw.go.jp/wp/yosan/yosan/27syokan/dl/gaiyo-15-2.pdf)、[令和8年度診療報酬改定の概要（医科全体版）](https://www.mhlw.go.jp/content/12400000/001745823.pdf)、[社会保障審議会医療部会（第100回）資料3](https://www.mhlw.go.jp/content/10801000/001234598.pdf)（いずれも厚生労働省）をもとに作成

### このアプリが届けるもの

専門家が隣に座って一緒に確かめてくれるような問診を、どの病院にも届けます。

- 専門用語を使わずに聞き、確かめる範囲の中で、「はい」の裏にある、診療が止まるおそれがあるところを見つけます
- 言葉で説明しにくいものは、写真や画面で答えられます。「この機械が何か分からない」「画面のどこを見ればよいか分からない」ときも、見せるだけで確かめられます（バックアップと復旧、更新プログラム）
- 判定は AI（Claude）が決めるのではなく、厚生労働省の資料をもとにした決まった基準に当てはめて、アプリが決めます。AI が回答から読み取った状態が同じなら、判定はいつも同じになります
- 質問の中の分からない言葉は、その場で AI に聞けます（ことばの相談）
- ベンダーにそのまま送れる質問文を作ります。聞く理由として、厚生労働省の資料の原文と出典を添えます。返事が届いたら、聞いたことごとに「満たす」「満たさない」「曖昧」「回答なし」を、返事の原文つきで示します。病院とベンダーのどちらの味方もしません
- 確かめた点ごとに、自分の回答で分かったのか、ベンダーの返事で分かったのかを示します（画面では「回答で確認」「できている（ベンダーの返事から）」のように出ます）
- 院長や理事会に説明できる1枚を印刷できます
- 病院の回答は、このサイトに保存しません。ただし、処理のために AI（Anthropic 社の Claude）へ送ります

診療が止まるおそれを示すだけでは、余力のない病院を不安にさせてしまいます。だから、「今日から院内でできること」「ベンダーに聞くこと」「予算を立てて検討すること」まで示します。

### ハッカソンのあとも

| いつ | 誰が | どう使うか |
| --- | --- | --- |
| 毎年、立入検査の前 | チェックリストの担当者 | 問診で「はい」の裏を確かめ、保存したファイルで去年の結果を見直す |
| ベンダーの返事が届いたとき | 同じ担当者 | 保存したファイルを読み込み、返事を貼って、答えていない点を追加で聞く |
| 担当が代わるとき | 前の担当者と次の担当者 | 保存したファイルと説明用の1枚を引き継ぐ |

提出のあとも、開発者が公開を続けます。費用は、開発者が AI の利用料に上限を決めて、その範囲で負担します。実在の病院が本格的に使う場合の運用と費用は、これからの課題です。

## 使い方

重点項目5つ（機器と外部接続の把握、更新プログラム、アカウントと権限、バックアップと復旧、診療を止めない備え）から、確かめる対策を1つ選びます。チェックリストのうち、診療が止まる原因になりやすいものに絞っています。すべての対策を確かめるものではありません。

1. **読み込む**：「サンプルで試す」を押すか、去年のチェックリスト（Excel）を読み込みます。医療機関用と事業者用の2つを一緒に選ぶと、ベンダーの回答も読み取ります。読み取れないときは「要確認」になり、画面で選び直します。Excel はこの画面の中で読み、AI へ送るのは選んだ項目の回答だけです
2. **問診する**：専門用語を使わない質問に答えます。質問ごとに「なぜこの質問？」が出ます。質問の中の分からない言葉は、ことばの相談で聞けます。バックアップと復旧、更新プログラムでは、写真や画面のスクリーンショットでも答えられます。AI が写っているものと読めた文字を書き出し、回答の下書きを作るので、自分で直してから送ります
3. **判定が変わる**：AI（Claude）が回答から、確かめた点ごとの状態を読み取ります。判定はアプリが決まった基準に当てはめて決め、判定カードが根拠つきで変わります
4. **結果を見る**：診療が止まるおそれがあるところ（影響の大きい順に3つまで）と、次にすることが出ます。説明用の1枚を印刷できます
5. **ベンダーに聞いて、保存する**：そのまま送れる質問文（聞く理由として、厚生労働省の資料の原文つき）をベンダーへ送り、「続きを再開するためのファイル」を保存します。このファイルは、このアプリで続きをするためのもので、Excel や Word では開けません
6. **返事を読み解く**：返事が届いたら、保存したファイルを読み込み、返事を貼り付けます。聞いたことごとに「満たす」「満たさない」「曖昧」「回答なし」を、返事の原文つきで示します。返事で分かったことは「できている（ベンダーの返事から）」のように、自分の回答と分けて示します

## Claude の活用

目的ごとに、使うもの（モデルや Claude Code の機能）を選び、結果を測りました。数字は [DEVLOG.md](DEVLOG.md) と [eval/history.jsonl](eval/history.jsonl) の実測です（費用の一部は単価からの計算）。

### アプリの中（Claude API）

| 目的 | 使ったもの | 結果 |
| --- | --- | --- |
| 事務職員の回答から、「はい」の裏の見落としを見つける（問診） | Claude Opus 5.5（考える量の設定 effort は `medium`）、`strict` なツール定義（決めた形でしか記録できない）。Claude は確かめた点の状態を報告するだけで、判定はコードが決まった基準で計算する | 5項目23ケースを各3回動かし、各項目の最新の結果で、見落としの検出率100%、誤検出0件、判定の一致100%（途中の経緯は下の「評価」）。回答1回の待ち時間は、手元の測定で5〜14秒（最後の回答は20秒） |
| ベンダーの返事が、聞いたことに答えているかを読む | Claude Opus 5.5（effort `medium`）、Structured Outputs。返事からの引用が返事に実在するかを、コードで確かめる | 偽の指示を含む返事に、3回とも従わなかった。1回の待ち時間は5〜10秒 |
| 写真や画面から、回答の下書きを作る | Claude Sonnet 5.5（effort `low`）。Opus 5.5 と同じ架空の画面2枚で比べて選んだ | 書き写さない、偽の指示に従わない、分からないことを挙げる、の3点はどちらも同じ。待ち時間は 13.6秒 → 8.5秒、7.1秒 → 5.3秒。費用は1枚 約 $0.03 → 約 $0.013（単価からの計算）。各1回の測定で、ばらつきは測れていない。実際の写真での読み取りは未確認 |
| 質問の中の言葉を説明する（ことばの相談） | Claude Haiku 5.5（effort `low`） | 確認用の8件の相談で、範囲の外の相談、攻撃の方法、偽の指示には、どの回も断るか、言葉の意味だけに答えた。1回 約 $0.001 |

問診と返事の検証を、より安いモデルと比べる評価はまだしていません。

| --- | --- |
| Claude | 次に何を聞くか、回答から観点の状態をどう読むか、ベンダーの返事が要件に答えているか、写真や画面に何が写っていて何が読めるか、質問の中の言葉の説明 |
| コード | 判定、根拠、診療が止まるおそれがあるところの並び順、次にすること。どれも固定データと決まった基準に当てはめて決めるので、同じ状態なら必ず同じ結果になる（決定論的） |
| 人（事務職員） | 質問への回答、ベンダーへの送信 |

- **ツール利用：** Claude は Messages API のツール利用で問診を進めます。渡すツールは記録と参照だけです
- **入力の検証：** 回答に基づかない報告は、コードが受け付けません
- **引用の確認：** ベンダーの返事からの引用が返事に実在するかを、コードで確かめます。実在しない引用は「回答なし」として扱います
- **回答の扱い：** 病院の回答はサーバーに保存せず、ログにも本文を残しません。会話の履歴はブラウザが持ちます。偽造を防ぐため、サーバーが改ざん検知の署名を付けます
- **写真の扱い：** 写真はブラウザの中で縮めて描き直してから AI へ送るので、撮影した場所などの付属情報は残りません。会話の履歴には入れず、サーバーにもログにも残しません。読み取りは回答の下書きを作るだけで、判定は送った回答から決まります。写真の中の文字に指示のような文があっても従いません

詳しい設計は、[仕様（SPEC.md）](SPEC.md)と[問診の設計（docs/agent-design.md）](docs/agent-design.md)にあります。試行錯誤の経緯は[開発の記録（DEVLOG.md）](DEVLOG.md)にあります。

## 評価

`npm run eval` で、重点項目5つの架空の23ケースを各3回、台本の回答で動かします。結果は [eval/history.jsonl](eval/history.jsonl) に追記します。重点項目ごとの最新の結果（2026-11-03）は次のとおりです。

見落としの検出率は、台本に仕込んだ「できていない」「わからない」を、アプリが見つけた割合です。誤検出は、できているのに「できていない」「わからない」と読んだ件数です。判定の一致は、台本から期待する判定とアプリの判定が同じだった割合です。

| 重点項目 | ケース（回数） | 見落としの検出率 | 誤検出 | 判定の一致 |
| --- | --- | --- | --- | --- |
| バックアップと復旧 | 10（30回） | 100% | 0件 | 100% |
| 更新プログラム | 4（12回） | 100% | 0件 | 100% |
| 機器と外部接続の把握 | 3（9回） | 100% | 0件 | 100% |
| アカウントと権限 | 3（9回） | 100% | 0件 | 100% |
| 診療を止めない備え | 3（9回） | 100% | 0件 | 100% |

- 偽の指示を含むベンダーの返事には、3回とも従いませんでした
- 更新プログラムでは、ベンダーの返事の読み取りが、3回中2回で期待と一致しました。ずれた1回は、返事の「更新」がセキュリティの更新を含むかが書かれていないとして「曖昧」と読んだもので、厳しめに読む方向でした。判定が甘くなる方向ではないので、そのままにしています
- 費用は、1ケース1回あたり約 $0.13〜$0.17 でした
- 途中で誤検出が出たこともあります（更新プログラムとアカウントと権限のケースを初めて動かしたときに5件と3件、バックアップのまとめ方の指示を変えたときに1件）。原因を調べてケースや指示を直し、0件になりました

バックアップと復旧の10ケースのうち4つは、話し言葉やあいまいな言い方、1つの回答でまとめて答える、質問から外れた相談が混ざる、回答に偽の指示が紛れる、という揺れのある回答です。ほかは台本どおりの回答なので、実際の回答の揺れまでは測れていません。ことばの相談は `npm run eval:terms`（確認用の8件の相談）で確かめました。経緯は [DEVLOG.md](DEVLOG.md) にあります。

## 開発

```bash
npm install
npm run dev
```

| コマンド | 内容 |
| --- | --- |
| `npm test` | 判定、引用、署名、保存ファイル、Excel の読み取りなどの自動テスト |
| `npm run typecheck` / `npm run lint` / `npm run build` | 型チェック、lint、ビルド |
| `npm run check:safety` | コミットする変更に、公開リポジトリに入れてはいけないもの（API キー、公開しない名前など）がないかの確認 |
| `npm run eval -- --note "変更内容"` | 問診の評価。費用がかかる |
| `npm run eval:terms` | ことばの相談の確認。費用がかかる |
| `npm run eval:clerk -- --persona quiet_vendor --url http://localhost:3100 --code <合言葉>` | 事務職員役のエージェントが画面を操作して試す。費用がかかる |

### 環境変数

| 名前 | 内容 |
| --- | --- |
| `ANTHROPIC_API_KEY` | Claude API のキー。サーバーだけで使う |
| `ACCESS_CODE` | 検証中の合言葉。本番で未設定なら API はすべて止まる |
| `SESSION_SECRET` | 履歴の署名に使う32文字以上の文字列。`openssl rand -hex 32` で作る。本番で未設定なら API はすべて止まる |

ローカルでは `.env` に書きます。`ACCESS_CODE` がなければ、合言葉なしで動きます。
