# 待ち時間を区間ごとに測って直す

待ちの原因を推測で決めない。測ってから直し、直したら同じ条件で測り直す。

## 1. サーバーの中を測る

- `npm run eval:perf -- --runs 3 --rounds 6`（アプリと同じ設定。Opus 5.5 は fast mode）
- 比べるとき：`--standard`（ふつうの速さ）、`--model claude-sonnet-5-5` など（速さだけ。質は測らない）
- 出力の読み方
  - 「始まりまで」：通信と入力の読み込み。モデルや速さではほぼ縮まない
  - 「考える」：adaptive thinking。ここが長ければ effort を疑う
  - 「書く」：出力トークンにほぼ比例する。ここが長ければ、書く量（ツールの入力の長さ）か、書く速さ（fast mode、モデル）を疑う
  - ブロックの名前と `@秒`：どのツールをいつ書き終えたか。先に画面へ出せるものがあるかを見る
  - 呼び出しが2回の場面：往復が1回多い。減らせるかを見る
- 費用の目安：5場面の問診1回で、fast mode の Opus 約 $0.2、ふつうの Opus 約 $0.1

## 2. 画面の側を測る（サーバーの中で説明がつかないとき）

- 手元の本番ビルド（`.claude/launch.json` の `prod`）を Browser pane で開き、`fetch` に時刻を記録する仕掛けを `javascript_tool` で一時的に入れて、問診の流れを動かす
- サーバーのログ `[interview] 実測` の `ms` と、ブラウザが受け取り終えるまでの時間を比べる。差が通信と画面の分
- アプリのコードは変えずに測る

## 3. 直す

- 直すのは、測った区間に効くものだけにする
- 指示の文、ツールの形、モデル、effort を変えるときは、質が落ちないかを `npm run eval` で確かめる（1回の評価で変えるのは1つ。結果にばらつきがあるので、1回で決めない）。モデルを比べるときは `--model`。評価はふつうの速さが既定で、アプリと同じ fast mode で測るときは `--fast`
- 画面の流れを変えたら `npm run test:e2e`。問診や返事の流れを変えたら `npm run test:e2e:paid` を1回

## 4. 測り直して記録する

- 直す前と同じ条件（同じ `--runs`、`--rounds`、項目）で測り直す
- `DEVLOG.md` に、前と後の表、何回測ったか、費用、やめた案を書く。推測の数字は書かない
- README の待ち時間を変えるときは、DEVLOG にある値だけを写す。測り方（手元から直接か、画面か）を断る
- 画面の待ちの案内（`src/lib/wait.ts`）の秒数も、実測に合わせて見直す
